# 0002. develop → release → main の順に配布物を作る

- ステータス：Accepted
- 日付：2026-09-30
- 関連 Issue：なし

## コンテキスト

GitHub の Template Repository は既定ブランチ（`main`）の内容をコピーするため、`main` はテンプレートとしてそのまま使える状態に保つ必要がある。

一方、テンプレートの開発には配布しないもの（開発ガイド、配布物を作るワークフロー・スクリプト、開発専用の規約・フック等）が必要になる。

## 検討した選択肢

- 開発専用のものも `main` に置く：テンプレートから作成したリポジトリにそのままコピーされる
- 開発用のブランチから、開発専用のものを除いた内容を `main` に反映する。反映するコミットの親の付け方は次のどちらか
  - `main` だけを親にする：`main` の履歴から反映元のコミットをたどれない
  - `main` と反映元の両方を親にする：`main` の履歴から反映元をたどれる

## 決定

`develop`（開発）→ `release`（リリース候補）→ `main`（配布用）の3ブランチで運用する。

- `develop` → `release` は PR でマージする。マージ方法は Merge commit のみにする（squash すると `develop` と履歴が分岐し、以降の PR でコンフリクトするため）
- `release` への push で `release-to-main` ワークフローが、`main` を起点にツリーを `release` の内容で置き換えて開発専用のものを除き、`main` への PR を作る。ツリーを丸ごと置き換えるため、`main` の履歴に関係なくコンフリクトしない
- 反映するコミットは `main` と `release` の両方を親にする。squash すると親が失われるため、`main` のマージ方法も Merge commit のみにする
- ワークフローの push・PR 作成には PAT（`RELEASE_PR_TOKEN`）を使う。`GITHUB_TOKEN` ではワークフローファイルを含むコミットを push できず、作成した PR で CI も起動しないため

## 結果

- `main` は常にテンプレートとしてそのまま使える状態になり、`main` の履歴から反映元の `release` をたどれる
- `main` の履歴には開発専用のファイルを含むコミットが入る。ただし「Use this template」は履歴をコピーしないため、配布先には影響しない
- PAT の有効期限が切れるとワークフローが失敗するため、期限前に更新する必要がある
